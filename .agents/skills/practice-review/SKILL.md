# 연습 코드 리뷰

사용자가 **이미 스스로 답을 낸 뒤**에 부르는 스킬이다. 여기서는 힌트만 주고 물러설 필요는 없다.
다만 목적은 여전히 학습이므로, 고친 코드를 통째로 던지는 대신 **왜 그런지**를 남긴다.

## 기준선: 연습 문제 수준

이 저장소는 알고리즘 풀이와 유틸 함수 직접 구현이 목적이다.
**프로덕션 코드가 아니다.** 실무 기준을 그대로 들이대면 배울 것보다 소음이 많아진다.

그래서 리뷰는 세 칸으로 나눈다. 이 구분 자체가 이 스킬의 핵심이다.

### 1. 꼭 고칠 것

지금 이 코드가 **틀렸거나, 알고리즘의 목적을 달성 못 하는** 것.

- 반환값 누락, 엣지 케이스 미처리 — 반례를 같이 준다
- 의도한 복잡도에 도달 못 함 — "해시맵 힌트를 봤는데 O(n²)로 남아 있다"
- 문제 제약 위반 — 같은 원소 두 번 사용 등
- 조기 종료가 불가능한 구조 (`forEach` 안에서 return 등)

여기 있는 건 반드시 고쳐야 한다. 다만 **어디가 왜 문제인지까지만** 말하고, 수정은 사용자가 한다.
사용자가 두 번 이상 막히면 그때 코드를 보여준다.

### 2. 스타일 · 가독성

동작은 맞지만 더 나아질 수 있는 것.

- 네이밍 (자세한 건 `/naming`)
- 중간 변수로 조건에 이름 붙이기 — `if (arr.length >= fn.length)` → `if (hasEnoughArguments)`
- 중첩 깊이, early return으로 평탄화
- `noExcessiveCognitiveComplexity` 경고 유발 지점
- 주석이 코드와 어긋나 있는지 (코드는 고쳤는데 하단 처리 설명이 그대로인 경우)

제안이지 지시가 아니다. 사용자가 안 고쳐도 되는 것들이다.

#### 공백 · 포맷 — diff 관점에서 본다

**`npx biome check <파일>`을 실제로 돌려서 확인한다.** 눈으로 짐작하지 않는다.

공백과 포맷은 취향 문제로 보이지만 **협업에서는 diff 품질 문제**다.

- **설정과 실제가 어긋나면 지적한다.** 이 저장소는 탭 들여쓰기인데 파일이 공백이면,
  나중에 누군가 포맷터를 돌리는 순간 **바뀐 줄이 하나인데 diff에는 파일 전체가 잡힌다.**
  리뷰어는 무엇이 실제 변경인지 구분할 수 없게 된다
- 후행 공백, 파일 끝 개행 누락도 같은 이유로 짚는다
- 정렬을 맞추려고 넣은 여분의 공백은 피한다. 한 줄이 바뀌면 주변 줄까지 diff에 딸려온다

**빈 줄은 문단 나누기다.**

- 모든 문장 사이에 빈 줄을 넣으면 빈 줄이 아무 의미도 전달하지 못한다
- 관련된 문장은 붙이고, **관심사가 바뀌는 지점에만** 넣는다
  (값을 준비하는 부분 / 판단하는 부분 / 행동하는 부분)
- 함수 첫 줄과 마지막 줄에는 빈 줄을 두지 않는다

**일관성이 개별 규칙보다 우선한다.**

같은 파일 안에서 두 스타일이 섞여 있으면, 어느 쪽이 더 나은지와 무관하게 하나로 통일하라고 말한다.
같은 개념에는 같은 단어를 쓴다 — `diffValue`와 `matchedIndex`처럼 한쪽만 리네이밍되어
짝이 안 맞는 상태도 여기 해당한다.

### 3. 참고 — 여기선 과함

**이 칸을 비우지 말 것.** 사용자가 "실무였으면 이런 것도 본다"를 알되,
지금 적용하면 과하다는 걸 같이 알게 하는 게 이 리뷰의 목적 중 하나다.

각 항목마다 반드시 두 가지를 붙인다.

- **왜 지금은 과한가** — "입력이 항상 유효하다고 문제에 명시돼 있다"
- **언제 필요해지는가** — "이 함수를 여러 곳에서 쓰게 되면 그때"

이 칸에 들어갈 만한 것들:

- 제네릭·조건부 타입으로 타입 확장
- 입력 유효성 검사, 방어적 프로그래밍
- 커스텀 에러 클래스, 에러 바운더리
- 인터페이스 추출, 의존성 주입
- 마이크로 최적화 (입력 크기가 10^4인데 상수 배 줄이기)
- 과도한 추상화 — 한 번밖에 안 쓰는 헬퍼 분리

반대로, **연습 문제여도 양보하지 않는 것**들은 1·2번으로 올린다.
복잡도, 정확성, 이름 — 이 셋은 과제 테스트에서 그대로 평가받는다.

## 성능은 항상 숫자로

"느릴 수 있다"가 아니라 복잡도를 적는다.

- 현재: 시간 `O(?)`, 공간 `O(?)` — 어느 줄 때문인지
- 개선 가능하다면 도달 가능한 복잡도와 **어떤 자료구조가 그걸 가능하게 하는지**
- 트레이드오프를 명시한다. 시간을 줄이려 공간을 O(n) 쓰는 게 이 문제에선 타당한지

제약 조건을 근거로 삼는다. `nums.length <= 10^4`면 O(n²)는 10^8이라 위험하다 — 이런 식으로.

## 진행 방식

1. 먼저 **잘한 부분**을 하나 짚는다. 빈말이 아니라 실제로 나아진 지점을 찾는다
2. **직접 돌려보고 나서 말한다** — 추측으로 리뷰하지 않는다
   - `npx vitest run <파일>` — 테스트 통과 여부
   - `npx tsc --noEmit` — 타입 에러. 통과해도 `strict` 설정이 꺼져 있는지 확인한다
   - `npx biome check <파일>` — 포맷·린트
3. 세 칸으로 나눠 제시 — 1번이 없으면 "정답입니다"라고 분명히 말해준다
4. 커버되지 않은 엣지 케이스를 제안한다
5. 끝에 확장 질문 하나 — "입력이 정렬돼 있다면 더 나은 방법이 있을까요?"

## 하지 말 것

- 전체 재작성본 제시. 사용자 코드의 구조를 유지한 채 지점을 짚는다
- 세 칸을 뭉뚱그려 나열하기. 중요도 구분이 사라지면 리뷰가 아니라 잔소리가 된다
- 사용자가 학습 기록으로 남긴 주석 처리된 시도들을 "정리하세요"라고 하기
- 지적만 20개 나열하기. 많으면 중요한 3~5개로 추리고 나머지는 있다는 것만 알린다
