# 요구사항 분석 노트

구현 **전에** 쓰는 노트를 돕는 스킬이다. 코드보다 이 노트가 먼저다.

## 이 스킬의 절대 조건

**노트를 대신 채워주지 않는다.**

여기서 "처리" 항목을 대신 써주면 그건 알고리즘을 통째로 넘겨준 것이다.
구현만 안 했을 뿐 정답을 준 것과 같다. `AGENTS.md`의 원칙이 이 스킬에서 가장 강하게 적용된다.

- 빈 템플릿을 제시한다 → 사용자가 채운다 → **채운 걸 검토한다**
- 검토는 "빠진 칸", "서로 모순되는 항목", "이 입력이면 어떻게 되나요?" 질문까지
- 사용자가 처음부터 막혀 있으면 처리 단계를 알려주는 게 아니라
  **"먼저 목적 한 문장부터 써보세요"** 하고 앞 칸으로 되돌린다

## 노트 위치 (기존 컨벤션)

- **파일 상단** — 문제 원문. 요구사항, 제약 조건, 예제
- **파일 하단** — 분석 노트

`async-task-queue.ts`, `twoSum.ts`가 이미 이 구조다. 유지한다.

## 템플릿 A — 알고리즘 문제

상태가 거의 없고 입력에서 출력으로 흐르는 경우.

```
/**
 * 목적:
 * (한 문장. "무엇을 반환하는가"로 쓴다)
 *
 * 입력:
 * (이름 - 타입 - 제약)
 *
 * 출력:
 * (형태와, 답이 없을 때는 무엇을 반환하는가)
 *
 * 흐름:
 * (구체적인 예시 하나를 골라 손으로 따라간다 — 아래 설명 참고)
 *
 * 처리:
 * (위 흐름을 일반화한 단계)
 *
 * 엣지 케이스:
 * (빈 입력 / 원소 1개 / 중복 / 음수 / 답이 없는 경우)
 *
 * 복잡도 예상:
 * 시간 O(?)  공간 O(?)
 */
```

## 템플릿 B — 클래스·유틸 구현

시간에 따라 상태가 변하는 경우. `AsyncTaskQueue` 류.

```
/**
 * 요구사항 분석하기
 *
 * 목적:
 * (한 문장)
 *
 * 흐름:
 * (구체적 시나리오 트레이스)
 *
 * 필요한 데이터 구분:
 * - 보존: (반드시 들고 있어야 하는 것)
 * - 파생: (보존 데이터로 계산 가능한 것)
 *
 * [메서드명]
 * 입력 / 처리 / 출력 / 부수효과
 *
 * 불변식:
 * (항상 참이어야 하는 조건)
 */
```

## 핵심 1 — 흐름은 반드시 구체적 예시로

가장 중요한 칸이고, 가장 자주 생략되는 칸이다.

일반론으로 쓰면("배열을 순회하며 조건을 확인한다") 아무것도 검증되지 않는다.
**입력값을 하나 정하고 손으로 끝까지 따라가야** 빠진 게 드러난다.

`async-task-queue.ts`가 좋은 예다.

```
최대 동시 개수가 2로 가정
[task1] 실행
[task1, task2] task2 실행
task3 대기열에 추가
task1 작업이 끝나면, task3이 추가되어야함
```

이렇게 쓰니까 "작업이 끝나는 시점에 다음 걸 꺼낸다"는 핵심이 저절로 나왔다.
`twoSum.ts`에는 이 칸이 없다. 있었다면 `[3, 3]` 케이스를 훨씬 일찍 만났을 것이다.

**예시는 가장 단순한 것 말고 두 번째로 단순한 것을 고른다.** 정상 케이스 하나, 까다로운 것 하나.

## 핵심 2 — 보존 데이터와 파생 데이터

이 구분이 설계 품질을 결정한다.

- **보존 데이터** — 계산으로 복원할 수 없어 반드시 들고 있어야 하는 것 (= 상태)
- **파생 데이터** — 보존 데이터로부터 언제든 계산되는 것

**원칙: 파생 데이터를 상태로 저장하지 않는다.**
저장하는 순간 원본과 어긋날 수 있고, 그 동기화가 버그의 주 원인이 된다.

`AsyncTaskQueue`에서 이미 이걸 지키셨다.

- 보존: `concurrency`, `runningTaskCount`, `pendingQueue`
- 파생: "한도에 도달했는가" → 필드가 아니라 `hasReachedConcurrencyLimit()` 메서드

이걸 `isFull` 같은 boolean 필드로 뒀다면 값을 올릴 때마다 갱신해야 하고,
한 군데만 빠뜨려도 큐가 멈춘다.

검토할 때 던질 질문:

- 이 필드는 다른 필드로 계산 가능한가? → 가능하면 메서드로 내린다
- 두 필드가 항상 같이 바뀌어야 하는가? → 둘 중 하나는 파생일 가능성이 높다
- 이 상태를 지우면 무엇을 복원 못 하는가? → 아무것도 없으면 필요 없는 상태다

## 핵심 3 — 불변식

"항상 참이어야 하는 조건"을 한 줄로 적게 한다. 버그를 찾는 잣대가 된다.

- `runningTaskCount`는 절대 `concurrency`를 넘지 않는다
- `runningTaskCount >= 0`
- 대기열의 순서는 추가된 순서와 같다

## 검토 순서

사용자가 채운 노트를 받으면 이 순서로 본다.

1. **목적이 한 문장인가** — 두 문장이면 함수가 두 개일 수 있다
2. **흐름이 구체적 값으로 쓰였는가** — 일반론이면 예시를 요구한다
3. **엣지 케이스가 흐름과 모순되지 않는가** — 반례를 던져 확인한다
4. **파생 데이터가 보존 쪽에 섞여 있지 않은가**
5. **복잡도 예상이 제약 조건과 맞는가** — `n <= 10^4`에 O(n²)면 짚는다
6. 여기까지 통과하면 **"이제 구현해보세요"** 하고 물러선다

## 구현 후

노트와 실제 코드가 어긋났는지 확인한다. 어긋났다면 둘 중 하나다.

- 구현 중에 더 나은 방법을 찾았다 → **노트를 고친다.** 왜 바뀌었는지 한 줄 남기면 더 좋다
- 노트대로 못 했다 → 왜 막혔는지가 다음에 볼 학습 기록이다

`curry.ts`처럼 시도했다 실패한 흔적을 주석으로 남기는 습관과 이어진다. 지우라고 하지 않는다.
